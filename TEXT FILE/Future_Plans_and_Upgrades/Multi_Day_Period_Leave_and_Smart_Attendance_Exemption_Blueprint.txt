1. EXECUTIVE OVERVIEW & PROBLEM STATEMENT
================================================================================
Currently, the SmartAttend leave management and attendance tracking subsystems 
operate with two critical operational limitations:

1. Single-Day Leave Restriction:
   Students can only apply for leave on a single designated date. If a student is
   hospitalized, has medical bed rest, or has a family emergency requiring 2, 5, 
   7, or 10 days of absence, they are forced to submit multiple repetitive single-day
   requests or submit a single date that fails to cover the entire absence window.

2. Disconnected Attendance & False-Positive Absent Notifications:
   When a student is legitimately on medical or approved leave (e.g., from Oct 26 
   to Oct 31), and a professor conducts a lecture or lab session on Oct 26:
   - The student does not appear in front of the camera or face scan and is 
     automatically or manually flagged as "Absent".
   - Upon saving attendance, SmartAttend's automated alert system fires an "Absenteeism
     Notification" email to both the student and their parents.
   - This causes panic, confusion, and administrative overhead, as parents receive 
     absent warnings for dates their ward had already formally applied for leave.

This blueprint outlines the complete end-to-end design to enable multi-day period 
leave applications, real-time visual badges/highlights in professor attendance panels, 
automated suppression of absent notifications for leave students, and seamless 
attendance record synchronization.

2. FUNCTIONAL REQUIREMENTS SUMMARY
================================================================================
[FR-1] Multi-Day Period Leave Application:
       Students can select a single date OR specify a date range (Start Date and 
       End Date) or select duration in days (e.g., 2, 5, 7, 10 days). The system 
       automatically calculates and validates the total duration.

[FR-2] Comprehensive Parent Notification:
       When a multi-day leave is submitted, the automated email sent to parents 
       explicitly displays the full date range (e.g., "From: 26 Oct 2026 To: 31 Oct 2026")
       and the total duration ("6 Days"), alongside the reason and medical proof status.

[FR-3] Professor Roster Visual Highlighting:
       When a professor initializes an attendance session (Face Scan, Lab Attendance, 
       or Manual Attendance) on any date D, the system cross-references all active 
       leaves. Any student whose leave window includes date D is visually highlighted 
       with a prominent status badge (e.g., "ON APPROVED LEAVE: 26 Oct - 31 Oct").

[FR-4] Automatic Absent Notification Suppression:
       When the professor saves the attendance session or clicks the "Absent" button,
       any student who is highlighted as being on approved/applied leave is strictly 
       EXCLUDED from the absent email dispatch list. Neither the student nor the 
       parent receives an absenteeism alert for that day.

[FR-5] Attendance Synchronization:
       The student's attendance for that session is recorded with status 'Leave' / 'Excused',
       updating their attendance profile in real time alongside their peers without 
       mischaracterizing their absence as an unauthorized proxy or bunk.

3. DATABASE ARCHITECTURE & SCHEMA ENHANCEMENTS
================================================================================
To support multi-day leave ranges while maintaining 100% backward compatibility 
with legacy single-day records, the following modifications will be made to 
the Supabase PostgreSQL schema.

A. Enhancements to `LeaveRequests` Table:
------------------------------------------
Columns to Add / Standardize:
- `startDate` (DATE, NOT NULL): The starting date of the leave period (YYYY-MM-DD).
- `endDate`   (DATE, NOT NULL): The concluding date of the leave period (YYYY-MM-DD).
- `durationDays` (INTEGER, NOT NULL DEFAULT 1): Number of days inclusive (endDate - startDate + 1).
- `leaveType` (VARCHAR(50) DEFAULT 'Medical'): 'Medical', 'Academic', 'Personal', 'Emergency'.
- `date`      (DATE): Retained for backward compatibility (maps directly to startDate).

PostgreSQL SQL Migration:
```sql
ALTER TABLE "LeaveRequests" 
  ADD COLUMN IF NOT EXISTS "startDate" DATE,
  ADD COLUMN IF NOT EXISTS "endDate" DATE,
  ADD COLUMN IF NOT EXISTS "durationDays" INTEGER DEFAULT 1,
  ADD COLUMN IF NOT EXISTS "leaveType" VARCHAR(50) DEFAULT 'Medical';

-- Backfill legacy records where only `date` exists
UPDATE "LeaveRequests"
SET "startDate" = "date",
    "endDate" = "date",
    "durationDays" = 1
WHERE "startDate" IS NULL AND "date" IS NOT NULL;

-- High-performance index for rapid date-range matching during attendance sessions
CREATE INDEX IF NOT EXISTS idx_leaverequests_student_range 
ON "LeaveRequests" ("studentId", "startDate", "endDate", "status");
```

B. Enhancements to `AttendanceHistory` Table:
---------------------------------------------
- Ensure the `status` column accepts `'Leave'` or `'Excused'` in addition to 
  `'Present'`, `'Absent'`, and `'Late'`.
- Add an optional foreign key `leaveRequestId` (BIGINT NULL) linking the attendance 
  row directly to the approved leave record for auditable compliance.

B. Client-Side Validation Logic (in `backend/student_dashboard.js`):
-------------------------------------------------------------------
```javascript
function calculateLeaveDuration() {
    const startVal = document.getElementById('leaveStartDate').value;
    const endVal = document.getElementById('leaveEndDate').value;
    const durationBadge = document.getElementById('leaveDurationBadge');

    if (!startVal || !endVal) {
        durationBadge.innerText = 'Select valid dates';
        return 0;
    }

    const start = new Date(startVal);
    const end = new Date(endVal);

    if (end < start) {
        showToast('End date cannot be earlier than start date!', 'error');
        document.getElementById('leaveEndDate').value = startVal;
        return 1;
    }

    // Difference in calendar days inclusive
    const diffTime = Math.abs(end - start);
    const diffDays = Math.ceil(diffTime / (1000 * 60 * 60 * 24)) + 1;

    durationBadge.innerHTML = `<i class="fa-solid fa-calendar-days"></i> Total Duration: <strong>${diffDays} Day(s)</strong>`;
    return diffDays;
}
```

---------------------------------------------

  `SmartAttend — Leave Application Submitted: [Student Name] ([Duration] Days)`

* Professional HTML Email Template Content:

  - Leave Period: From [Start Date] to [End Date] (Formatted: "26 Oct 2026 to 31 Oct 2026")
  - Total Duration: [X] Days
  - Stated Reason: [Student Reason]
  - Medical Document: [Attached / Under AI Verification]
  - Status: "Submitted — Awaiting Professor Review"

-------------------------------------------------

  `SmartAttend — Medical Leave Approved: [Student Name] (26 Oct 2026 to 31 Oct 2026)`
- Explicitly states: "Attendance records for lectures occurring within this 6-day window will be recorded as Authorized Leave."

   `GET /api/attendance/active-leaves?dept=BCA&date=2026-10-26`

   ```javascript
   const { data: activeLeaves } = await supabase
     .from('LeaveRequests')
     .select('studentId, studentName, startDate, endDate, durationDays, reason, status')
     .eq('status', 'Approved') // or include 'Pending' based on college policy
     .lte('startDate', sessionDate)
     .gte('endDate', sessionDate);
   ```

   ```javascript
   const leaveMap = new Map();
   activeLeaves.forEach(l => leaveMap.set(l.studentId.toUpperCase(), l));
   ```

7. SMART ABSENTEEISM SUPPRESSION: BLOCKING ABSENT EMAILS FOR LEAVE STUDENTS
================================================================================
Affected Files:
- `server/server.js` (lines 3090-3150 and 3760-3840)

A. The Core Problem to Solve:
-----------------------------
When a professor completes attendance, the backend iterates over all students marked 
`status === 'Absent'` and triggers `sendEmail` with `getParentAbsentAlertTemplate`.
If student `23BCA101` is marked absent, they would erroneously receive an alert.

B. Backend Suppression Interceptor Logic:
-----------------------------------------
Inside `server.js` where absent emails are collected:

```javascript
// Step 1: Extract all student IDs initially flagged as absent
const rawAbsentStudents = (students || []).filter(s => (s.status || '').toLowerCase() === 'absent');

if (rawAbsentStudents.length > 0) {
  const sessionDate = attendanceDate || new Date().toISOString().split('T')[0];

  // Step 2: Query all active leaves covering this specific lecture date
  const absentIds = rawAbsentStudents.map(s => String(s.id).trim().toUpperCase());
  
  const { data: activeLeaves } = await supabase
    .from('LeaveRequests')
    .select('studentId, status')
    .in('status', ['Approved', 'Pending']) // Exempt both approved & pending leaves
    .lte('startDate', sessionDate)
    .gte('endDate', sessionDate);

  const exemptedStudentIds = new Set(
    (activeLeaves || []).map(l => String(l.studentId).trim().toUpperCase())
  );

  // Step 3: Filter OUT any student who has an active leave
  const eligibleAbsentStudents = rawAbsentStudents.filter(s => {
    const sId = String(s.id).trim().toUpperCase();
    if (exemptedStudentIds.has(sId)) {
      console.log(`[ALERT SUPPRESSED] Student ${sId} is on formal leave on ${sessionDate}. Suppressing absent email.`);
      return false; // DO NOT SEND ABSENT EMAIL
    }
    return true; // Send standard absent alert
  });

  // Step 4: Dispatch emails ONLY to genuinely absent students
  for (const absStudent of eligibleAbsentStudents) {
    // Standard Parent & Student Absent Alert Dispatch...
  }
}
```

Key Advantage:
- 100% Guaranteed zero false-positive emails to parents.
- No spam or anxiety for parents whose children are recovering from illness or on permitted leave.

8. ATTENDANCE RECORD SYNCHRONIZATION & STATISTICAL INTEGRITY
================================================================================
When the professor saves attendance:

1. Database Storage:
   - Students present -> Recorded as `'Present'`.
   - Students absent (unexcused) -> Recorded as `'Absent'`.
   - Students on leave -> Recorded as `'Leave'` in `AttendanceHistory`.

2. Percentage & Calculation Rule:
   Institutions handle leave attendance in one of two standard ways (configurable in `Setting.html`):
   - Option A (Exempt Model - Recommended): Total lectures attended = N, Total lectures conducted = (Total - Leave Days). The percentage is not penalized.
   - Option B (Medical Duty Credit Model): Days with approved medical leave are marked with an asterisk (*) and credited towards the mandatory 75% university eligibility requirement.

3. Analytics Dashboard Visibility:
   - On the Professor and Student analytics charts, attendance splits into:
     [ Present: 85% ]   [ Leave: 10% ]   [ Absent: 5% ]
   - Gives professors, HoDs, and university auditors complete transparency.

9. EDGE CASES, SECURITY & VALIDATION RULES
================================================================================
1. Date Overlap Prevention:
   - A student cannot submit two overlapping leave requests (e.g., submitting 26-29 Oct and then submitting 28-31 Oct). The system checks for range collisions and prompts the student to update the existing request.

2. Maximum Period Limit:
   - Set a maximum continuous leave threshold (e.g., 15 days). Leaves exceeding 15 days trigger an advisory prompt requiring HoD / Principal approval.

3. Weekend & Holiday Inclusion:
   - System displays an informational note: "Your leave includes 2 weekend days (Saturday & Sunday). Total academic lecture days affected: 5 days."

4. Pending vs. Approved Leaves on Attendance Screen:
   - Approved Leaves: Displayed with Green/Cyan badge (`[APPROVED LEAVE]`).
   - Pending Leaves: Displayed with Amber badge (`[LEAVE PENDING REVIEW]`).
   - Both suppress absent emails by default to prevent unfair penalization while the professor's review is pending.

5. Early Return / Cancellation:
   - If a student recovers early and attends class on Oct 28 (despite leave granted till Oct 31), when their face is recognized by the camera, the system automatically registers them as `Present` and records an early return note.
